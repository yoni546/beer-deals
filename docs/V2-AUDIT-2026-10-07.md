## 1. Why users see "משהו השתבש" and "לא הצלחנו לטעון"

Ranked by likelihood of causing the reported symptoms. All verified.

| # | Root cause | Location | Mechanism |
|---|---|---|---|
| 1 | Whole-feed reads run as the **`anon`** role and **throw** on failure | `src/lib/offers.ts:83,96,229,249` | `publicReader()` is a cookie-less anon client. Supabase gives `anon` a **3 s** `statement_timeout` (vs 8 s for `authenticated`). `offers_feed` costs ~1.2 s unfiltered at production scale, so a cold-cache read is a coin flip; a `57014` becomes a thrown `DataUnavailableError` → root error boundary → full-screen error. Intermittent because `unstable_cache` holds 300 s and **every admin action clears `FEEDS_TAG`** (`src/lib/actions/admin.ts:22`). |
| 2 | `getOfferByKey` filters on a **computed, un-indexable** column, uncached, serial | `src/lib/offers.ts:254-260` + `src/app/page.tsx:69` | `offer_key` is `'deal:'||d.id`. The filter cannot prune the `UNION ALL`, so one lookup computes the **entire** feed. Runs after the `Promise.all`, so its latency is additive, on **every Home render whenever a weekly deal is set** — the default editorial state. |
| 3 | One `Promise.all` per route, **one** error boundary app-wide | `src/app/page.tsx:60`, `beer/[slug]:47`, `store/[slug]:61`, `beer/page.tsx:15`, `store/page.tsx:10`; only boundary `src/app/error.tsx` | No try/catch in any server component; no `<Suspense>` islands. One failed decorative read (freshness) blanks the whole page exactly like a total outage. |
| 4 | `admin_overview()` computes `offers_feed` **three times**; the error is discarded | `supabase/migrations/0020_…sql:62-69`, `src/lib/admin-queries.ts:77` | Three unfiltered counts over the expensive view in one call. `if (error) return null` loses the distinction between timeout (`57014`), privilege refusal (`42501`) and bad argument (`22023`). This is the admin "לא הצלחנו לטעון את הנתונים". |
| 5 | `getViewer()` discards **all three** query errors | `src/lib/session.ts:58-64,74` | A timeout, pooler hiccup or RLS refusal collapses into "no profile, no favourites" → `src/app/page.tsx:49` redirects an onboarded user back to `/welcome`; an admin is bounced to `/admin/login`. Compounded by `isOnboarded` demanding **exactly 4** favourites. |
| 6 | `save_preferences` UPDATEs a profile row that may not exist | `supabase/migrations/0011_…sql:45-48` | No `insert … on conflict`, no row-count check. If the row is missing the UPDATE touches 0 rows, favourites still insert, the action reports success, `onboarded_at` stays null → a permanent onboarding loop that reports success every time. |
| 7 | Middleware mints a **new anonymous user** on any `getUser()` failure | `src/middleware.ts:35-45` | `getUser()` returns `{user:null}` for every failure, not just "no session" — including the refresh-token rotation race (the browser client auto-refreshes too). The branch is indistinguishable from a first visit, so the person's profile, favourites and admin row are replaced. Supabase also rate-limits anonymous sign-ins (~30/hour/IP), after which every visitor gets "לא הצלחנו להתחבר". |
| 8 | Server-action calls with no try/catch | `DealActions.tsx:57`, `ReportRow.tsx:25`, `ReportDealButton.tsx:28`, `AdminLogin.tsx:34` | The actions return `ActionResult` correctly, but a **rejected** request (504, lost network, "Failed to find Server Action" after a deploy) rejects inside the transition and React rethrows during render. Made likelier by `public/sw.js:54-65` caching `/_next/static/` cache-first under a hard-coded cache name that is never bumped. |
| 9 | Admin reads swallow errors into **empty states** | `src/lib/admin-queries.ts:17-47,82-94` | A failed read of the moderation queue renders "אין מבצעים שממתינים לאישור" — it tells an admin the queue is clear when the truth is "we could not look". The same mistake `CLAUDE.md` forbids for prices. |
| 10 | No `global-error.tsx`; `error.tsx` throws the error away | `src/app/error.tsx:11`, `src/app/layout.tsx:68` | The root layout does a Supabase round trip, and a root-segment boundary cannot catch its own layout → Next's unstyled English LTR page. **Nothing is logged anywhere; there is no monitoring integration at all.** |

Checked and cleared: there are **no `.single()` calls** in `src/` (every one-row read uses
`.maybeSingle()`), and no unsafe index access or non-null assertions on data. Those are not causes.

## 2. Why it feels slow

Measured TTFB already recorded in `docs/INFRASTRUCTURE.md:97-107` (from Israel, 5 runs):
`/whats-new` **3702 ms** median · `/beer/goldstar` **3987 ms** · `/store/rami-levy` **5328 ms**.

The bundle is **not** the problem (103 kB shared; no heavy dependency; the Server/Client split is
close to ideal). Four things dominate, in order:

1. **Geography.** `vercel.json:3` pins `hnd1` (Tokyo) because the Supabase project is in
   `ap-northeast-1` — correct relative to the database, but every byte crosses Israel↔Tokyo.
   All 20 routes are `force-dynamic`, so there is no cacheable shell: every navigation pays a
   full round trip (~250–500 ms floor before the server does anything).
2. **Prefetch fan-out.** `TabBar` (in the root layout, so on every screen) and `ListingSearch`
   use default `<Link>` prefetch pointing at `force-dynamic` routes. One page view fans out into
   up to four server renders; `/beer` renders ~40 prefetching rows, a chain page ~340 anchors.
3. **`offers_feed` has an irreducible whole-dataset cost**, by construction: the `store_min` and
   `market` CTEs are declared `as materialized`, which is an optimisation fence — a filter on one
   beer or one chain can never be pushed into them. This is the ~0.22–0.89 s floor that
   migration 0022's own header reports.
4. **Three full-screen SVG-filtered bitmap layers** (`feColorMatrix` → `feComponentTransfer` →
   `feGaussianBlur`, `position: fixed`) gate the LCP paint and re-composite on scroll.

Other verified items: middleware calls `supabase.auth.getUser()` — a network hop to Tokyo —
**before every request including every prefetch**; the catalogue (`beers`, `stores`, `skus`,
`app_settings`) is re-read from Tokyo on every request with `select("*")`; `/bottles/` has no
cache header and is not in the service worker, so the LCP image revalidates on every navigation;
list thumbnails are served as full-size hero assets (Home downloads ~292 KiB to draw four
19×72 px bottles); ~170 `ScopeLine` client islands hydrate per chain page.

## 3. Beer imagery — the real state

**Nothing is broken.** 34 beers; 33 have a theme identity (`somersby` is a cider, deliberately
excluded); 27 have a real product photo; every manifest entry resolves to a file and every file
is in the manifest; no dimension mismatches.

The four beers named in the brief are not broken images:
- **Desperados, 1664 Blanc (`kronenbourg`), Miller** — documented, deliberate gaps recorded at
  `scripts/fetch-bottles.mjs:74-83`. Retailer catalogues publish only cans/multipacks for the
  last two; cutting a bottle out of a pack shot would alter the photo, which the project forbids.
  They render a hand-drawn SVG stand-in, not a broken card.
- **Amsterdam does not exist anywhere in the repository** — not in the seeds, not in `themes.ts`,
  not in the ingest brand table. It cannot be shown at all. **This needs an owner decision**
  (Amstel? the "Amsterdam" lager sold in Israel?) before a catalogue row is added.

Also photoless: `bazelet`, `krombacher`, `estrella`.

The real defects are (a) the visual inconsistency of 7 drawn bottles beside 27 photographs, and
(b) **no thumbnail tier at all** — one size per beer, used for everything. Re-encoding measured:
a 216 px-tall WebP tier is **139 kB total for all 27 files, −89%**.

## 4. Admin analytics — per-metric verdict

Every "week" is a rolling 168 h window ending at query time, labelled "השבוע". Four different
notions of "today" coexist; the notification pipeline correctly uses `Asia/Jerusalem`, the
dashboard never does.

| Tile | Verdict | Why |
|---|---|---|
| מבצעים באוויר | **WRONG — double counts** | The page adds `deals.live` to `offers.live`, but `offers_feed` already `UNION ALL`s `deals_public` (= approved deals). Every approved manual deal is counted twice and the hint "N מהרשתות" is false. |
| הורדו | **WRONG** | Keys on `updated_at`, which the `deals_touch` trigger bumps on *any* UPDATE — editing an old rejected deal's note counts as a takedown this week. No takedown timestamp exists in the schema. |
| נשלחו ע״י משתמשים | **WRONG** | `count(*) from deals where created_at >= now()-7d` with no `created_by` filter — every deal an admin typed in is reported as sent by users. |
| נשלחו אי פעם | **WRONG** | Includes `kind='test'` rows written by `sendTestPush`. |
| נוספו | **SUSPECT** | A current-state snapshot, not an event count: `set_deal_status` nulls `approved_at`, so a deal approved Monday and removed Tuesday leaves this tile and enters "הורדו". |
| ממתינות לשליחה | **SUSPECT** | "pending" means "the worker has not processed this row", not "will be sent" — it includes events that will resolve to `expired`, `below_threshold`, `no_recipients`… |
| מבצעים שעומדים להיגמר | **SUSPECT** | Window built from `toISOString().slice(0,10)` — **UTC** calendar dates. Between Israeli midnight and 02:00/03:00 the window is anchored to yesterday. No `is_sample` filter. |
| אנשים שנרשמו / נרשמו השבוע | **SUSPECT (semantics)** | Counts *profiles*, and a profile is one per anonymous browser session. Phone + desktop + installed PWA = 3 "people". Not obtainable from this schema; the honest label is "devices". Also "נרשמו" means *onboarded* in one tile and *merely opened the app* in the next. |
| ממתינים לאישור | CORRECT | Caveat: the queue page caps at 50, the tile does not. |
| דיווחים פתוחים | CORRECT | |
| N אנשים הפעילו התראות | CORRECT | Uses `EXISTS`, correctly avoiding fan-out. |

Two inert features found: **the "send a notification" checkbox on manual deal creation does
nothing** (`admin_add_deal` INSERTs, but the enqueue trigger is `after update of status`), and
`approveDeal`'s success toast reports the *worker's whole-run* send count, not this deal's.

## 5. What exists vs what V2 needs

**Already built and reusable — do not reinvent:**
the primary-beer model (`user_favorite_beers.rank` PK, `profiles.primary_beer_id` kept true by a
trigger) already satisfies "a clearly identifiable favourite"; `RankedBeers` is a complete
reorder primitive with full keyboard parity; the design system (`Tape`, `Price`, `Chip`,
`Screen`, `EmptyState`, `Strip`, `OfferLine`); a three-level `data-motion` contract
(full/lite/off) with device-capability detection; a service worker that genuinely never caches
navigations; per-branch price data with `promotion_scope` already deciding chain-wide vs
per-branch claims; the notification pipeline (outbox + dedupe + Israel-local quiet hours +
`timingSafeEqual` on `CRON_SECRET`) with clean extension seams at `NotifySettings`,
`PushRecipient` and `PushOffer`.

**Does not exist at all (definitive):**
- **Any geo data.** `branches` has `name_he`, `city`, `address` — **no latitude/longitude**, no
  PostGIS, no earthdistance. `profiles` has no location and no radius. No map, no geolocation,
  no distance sort anywhere in `src/`.
- Any report path for **catalogue/chain offers** — the report button renders only for
  `origin === "legacy"` and `deal_reports.deal_id` FKs to `deals`. The bulk of the feed cannot be
  reported at all, at UI *or* DB level.
- Any "deal still active" concept — not even partially.
- User reputation, trust, contribution scoring.
- **An admin audit log.** Attribution is per-row and last-writer-wins; `set_deal_status` actively
  *erases* `approved_by`/`approved_at`. A rejection, removal, re-approval and edit leave no trace.
- Contributor attribution in any UI. `deals.created_by` is recorded but is not in `DEAL_COLUMNS`
  nor the `AdminDeal` type, so the moderation queue cannot show who submitted a deal. And
  `profiles.first_name` is owner-only by RLS, so **there is no way to render a contributor's name
  today** without a new SECURITY DEFINER function or a public display-name column.
- A real "week" for the weekly deal: it is one nullable `app_settings.weekly_deal_id` with no
  window, no expiry, no rotation — and because the FK is to `deals`, **a chain-feed offer can
  never be the weekly deal**.
- Admin roles beyond two flat tiers (`admin`, `super_admin`). No moderator. Enforcement itself is
  sound: every write goes through an RPC that re-checks in Postgres; no action is frontend-only.

**The four-beer rule is enforced in 18 places** (listed in the frontend workstream): client UI,
the Settings editor, the zod schema in `src/lib/actions/profile.ts:13-14`, `session.ts:74`, the
four-slot stage and its CSS, `FavouriteKeys`' `grid-cols-4`, and `save_preferences` in migration
0011. The table's own `check (rank between 1 and 4)` **already permits 1–4 and needs no change**.
An `aria-label` ("ארבע הבירות שלי, לפי הסדר") is also an e2e locator in 5 specs.

## 6. Owner decisions and blockers

1. **Region.** The largest single performance lever is moving the Supabase project to Frankfurt
   (`eu-central-1`) and Vercel to `fra1`. Supabase cannot move a project in place; this is a
   create-and-restore, and it is owner work. `docs/INFRASTRUCTURE.md:112-120` already describes
   the rehearsal path. **Nothing in this branch does it.**
2. **Branch coordinates.** The price-transparency Stores file supplies name, address and city —
   **not coordinates**. Branch lat/lng requires geocoding through an external provider, which
   needs a credential. V2 ships the schema, the provider abstraction and the admin coverage view;
   it does **not** invent coordinates. Outbound network is blocked in this container, so no
   geocoding was run here.
3. **Amsterdam** — which product is meant? (see §3).
4. **Notifications beyond favourite #1.** `PRODUCT.md` records "favourite #1 is the only beer that
   may send a notification" as the owner's brief. The V2 brief asks notifications to consider
   favourite beers plural. This is a product change, not a bug — `PRODUCT.md` is updated to match.
5. **Four favourites.** Likewise, `PRODUCT.md` says "each person has four ranked favourite beers".
   V2 makes it 1–4. Recorded as an owner decision.

## 7. Dependency vulnerabilities

**Updated 2026-10-09.** The original note here said all of them were devDependencies. That was
wrong as the tree stood later: `npm audit --omit=dev` reported four, including `next` itself.

`npm audit fix` (non-breaking) was applied: Next 15.5.26 → 15.5.27, plus `sharp` and
`source-map-js`. `npm run verify` passes on the new tree — 954 tests, 66 files, build green.

**Two remain, and both are refused deliberately.** `npm audit` offers only one fix for either:
`next@16.4.0`, a breaking major. Upgrading the framework by a major version unannounced, at the end
of a large feature branch, trades a documented low exposure for an undocumented large one. It is its
own piece of work, with its own rehearsal, and it belongs to the owner.

| Advisory | What it is | Exposure here |
|---|---|---|
| `next` (moderate) | Cache poisoning of SSG and ISR pages **in self-hosted applications** | The app runs on Vercel, not self-hosted, and the build output shows every route as `ƒ` — server-rendered on demand. There are no SSG or ISR pages to poison. |
| `postcss` (high) | Arbitrary `.map` file read via an attacker-controlled `sourceMappingURL` in a CSS comment | PostCSS runs at **build time**, over this project's own stylesheets. Nothing a user submits ever reaches it. It is a build-toolchain exposure, not a runtime one. |

Neither is nothing, and neither is a reason to ship Next 16 without a rehearsal. Re-check after
the Next 16 upgrade is planned on its own.

## 8. Security findings, and where each one ended

Three findings came out of the V2 review that were not simply bugs. All three are closed.

### M-1 · `deals.image_url` was anything at all — **closed in 0.17.1**

Validated as `z.string().optional()` and rendered to a *moderator* as a clickable link. Any
visitor — and every visitor gets an anonymous session automatically — could submit an otherwise
valid deal with `image_url` set to a `javascript:` URL and wait for an admin to press "צפייה
בתמונה שצורפה". That scheme executes in the current document regardless of `target="_blank"`, so
it is script execution inside a super admin's session, and `grant_admin` is one server-action call
away. `data:text/html` and a convincing look-alike host are the quieter versions.

Closed in three layers: the submission schema pins the value to this project's own
`/storage/v1/object/public/deal-images/` prefix; the admin row parses it and renders a link only
for `https:`, with `rel="noreferrer noopener"`, so the raw column value never reaches the
attribute; and migration 0029 adds `deals_image_url_is_https` so no future code path can store one
either. `tests/deal-image-url.test.ts` proves all three, including that the RLS insert policy
cannot be used to smuggle one in.

### M-2 · no limit on what one anonymous session could write — **closed in 0.21.0**

An anonymous session could write three things, and nothing counted any of them:

- **A deal, straight into the moderation queue.** `deals_submit` (0003) checks that a submission is
  theirs and `pending`; it does not check how many. A shell loop over the PostgREST endpoint could
  put ten thousand rows in front of the moderators and make the queue useless. **No server action
  is in that path**, so nothing in the app could have stopped it.
- **Feedback on an offer** (0031). `unique (offer_key, reported_by)` stops stuffing *one* offer and
  stops nothing across the feed: one session could file a verdict on every offer there is.
- **A public display name** (0030), shown on other people's screens beside a price.

Closed by migration 0033, in Postgres — for the same reason authorization is: the deal path is a
direct table insert under RLS, so a limit in a server action would be a limit on the polite route
only. A trigger and the two definer functions cover the app, a script and a hand-written PostgREST
request alike. The limits count the rows themselves in a window rather than keeping a ledger of
attempts, which would be one more thing able to drift from the truth it describes.

| What | Limit | Why that number |
|---|---|---|
| Deal submissions | 8/hour, 25/day per person | A person in a shop photographs a few labels. Rejected ones count too: being rejected a lot is the signal, and resetting the quota on rejection would reward it. |
| Offer feedback | 60/hour per person | High on purpose. Somebody answering "still there" down an aisle is who the feature is for; a limit that punished them would be the wrong trade. |
| Display name | 10/hour per person | Not load — the row is tiny. A name that changes every few seconds is a billboard, not a credit. Clearing it counts, because alternating is the obvious way round a limit that only counted setting it. |

Refusals raise SQLSTATE `54000` (`program_limit_exceeded`), deliberately **not** `42501`:
`describeDbError` turns that into "you have no permission for this", which would be a lie told to
somebody who simply found four deals tonight. The Hebrew message reaches the person, and says when
to come back.

**What this is not.** It is not a defence against a botnet: a thousand anonymous sessions are a
thousand quotas. It raises the one-session flood from a shell loop to real work and bounds what any
single account can do. Supabase's own limit on anonymous sign-ins (~30/hour/IP) is the layer above,
and it belongs to the hosted project rather than to the schema — see
`docs/PRODUCTION-GO-LIVE-CHECKLIST.md` item E.

### M-3 · the admin roster could not be read by an admin — **closed in 0.11.1**

Fixed with an `admins_read` policy in migration 0025. Nothing was exposed; the panel simply could
not show who the administrators were.
